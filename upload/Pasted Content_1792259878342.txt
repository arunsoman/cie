# PRD: Native Visualization via ViewSpec → G6

**Codename:** CIE-VIZ  
**Status:** Implementation-ready  
**Implementation language:** TypeScript adapter + Rust ViewSpec producer  
**Rendering substrate:** AntV G6 v5 (`@antv/g6`)  
**Source basis:** CIE PRD (FR-9, FR-40–44), feature-requirements.md (EV-01…09, VIS-01…19, ZM-01…16, LY-01…05, A11Y-01…05), and the G6 extension/layout/plugin/fisheye APIs  
**Purpose:** Make visualization a first-class citizen of the platform by defining a single, closed contract between CIE and G6, so that any semantic graph can be rendered by any registered G6 extension, in any layout, with fisheye enabled by configuration — without adding chart-specific code to CIE and without limiting the number of charts to a fixed catalogue.

---

## 1. Definition of "Native"

Visualization is native when all five of the following are true:

1. **CIE never knows what a chart is.** It emits `ViewSpec` — a semantic graph with epistemic metadata. It has no `ViewKind` enum, no chart name, no layout name, no colour.
2. **G6 never knows what a claim is.** It receives `GraphData` and draws it. Every honesty rule is expressed as a style mapping on `datum.data`, not as logic in the renderer.
3. **The adapter is the only bridge.** One function, `adapt(ViewSpec) → GraphData`, plus one `graphOptions(spec) → GraphOptions`. Adding a chart type never changes the adapter's contract.
4. **Fisheye is configuration, not implementation.** Enabling it is one object in `plugins[]`; G6's built-in plugin supplies the lens.
5. **The chart count is unbounded.** Any G6 extension category — Node, Edge, Combo, Layout, Plugin, Behavior, Transform, Theme, Palette, Animation — is a valid rendering surface. The catalogue is whatever has been registered.

## 2. Architecture

```text
┌──────────────────────────────────────────────────────────────────────┐
│ CIE (Rust)                                                            │
│   claim store · five gates · coverage · ConceptNode DAG · evidence    │
│                                    │                                  │
│                                    ▼                                  │
│                          ViewSpec (semantic graph)                    │
│            elements[] · edges[] · groups[] · gaps[] · footer          │
│            every element: displayMode, evidence, salience             │
└────────────────────────────────────┬─────────────────────────────────┘
                                     │  JSON over HTTP / stdio
                                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│ Viz adapter (TypeScript)                                              │
│   gate(spec)        → throws on unevidenced element                   │
│   adapt(spec)       → { nodes[], edges[], combos[] }                  │
│   graphOptions(spec) → G6 GraphOptions (node/edge/layout/plugins)     │
└────────────────────────────────────┬─────────────────────────────────┘
                                     │
                                     ▼
┌──────────────────────────────────────────────────────────────────────┐
│ G6 (rendering substrate)                                              │
│   register(ExtensionCategory.*, name, impl)   ← open surface          │
│   layout.type: any built-in or registered layout                      │
│   plugins: ['fisheye', 'minimap', 'edge-bundling', 'history', …]       │
│   renderer: 'canvas' | 'svg' | 'webgl'                                │
└──────────────────────────────────────────────────────────────────────┘
```

There is exactly **one** place where semantic honesty meets visual freedom: the adapter's `gate()`. Every renderer downstream is free to be as creative as G6 allows, because it only receives data that has already passed the gate.

## 3. The ViewSpec contract

### 3.1 Type

```typescript
export interface ViewSpec {
  /** Semantic graph — no chart type, no layout, no colour. */
  elements: ViewElement[];
  edges:    ViewEdge[];
  groups?:  ViewGroup[];

  /** Epistemic footer — always present, always rendered. */
  footer: EpistemicFooter;

  /** Incompleteness is inside the spec, never hidden outside it. */
  gaps:   Gap[];
  hidden: HiddenCandidate[];

  /** Attestation — makes cache, staleness and audit possible. */
  scope: ScopeAttestation;

  /** Optional render hints. Absent = adapter chooses. */
  layoutHint?:  LayoutHint;
  preferences?: Preferences;

  /** Content hash over everything above except itself. */
  contentHash: string;
}

export interface ViewElement {
  id:            string;              // stable across revisions
  elementKind:   ElementKind;         // concept | symbol | file | route | rule | …
  displayMode:   'Fact' | 'Inference' | 'Hypothesis' | 'Fog';
  label:         string;
  evidence:      EvidenceRef;         // REQUIRED — no element without it
  claimId?:      string;              // REQUIRED iff displayMode ≠ Fact
  counterArgument?: string;           // REQUIRED iff displayMode = Hypothesis
  fogReason?:    string;              // REQUIRED iff displayMode = Fog
  salience:      { factors: string[]; weight: number; whyShown: string };
  fields:        Record<string, unknown>;
  parentId?:     string;              // group / hierarchy containment
}

export interface ViewEdge {
  id:          string;
  source:      string;
  target:      string;
  edgeKind:    string;                // calls | reads | writes | exposes | …
  displayMode: 'Fact' | 'Inference' | 'Hypothesis';
  evidence:    EvidenceRef;
  counterArgument?: string;
}

export interface LayoutHint {
  strategy: 'dagre' | 'fruchterman' | 'radial' | 'grid' | 'circular'
          | 'compact-box' | 'concentric' | 'force' | string;   // any G6 name
  params?:  Record<string, unknown>;    // passed through to G6 untouched
}

export interface Preferences {
  fisheye?: {
    trigger?: 'pointermove' | 'click' | 'drag';
    d?: number; r?: number; maxR?: number; minR?: number;
    maxD?: number; minD?: number;
    scaleRBy?: 'wheel' | 'drag';
    scaleDBy?: 'wheel' | 'drag';
    showDPercent?: boolean;
  };
  minimap?:  boolean | { size?: [number, number]; position?: string };
  edgeBundling?: boolean;
  history?:  boolean;
  renderer?: 'canvas' | 'svg' | 'webgl';
}
```

### 3.2 Contract clauses

| ID | Clause | Testable by |
|---|---|---|
| VIZ-A-01 | `ViewSpec` contains no chart name, layout name, colour or pixel value | Schema test: reject unknown keys |
| VIZ-A-02 | Every element has `displayMode` | Type-level non-optional |
| VIZ-A-03 | Every element has `evidence` | Adapter gate throws |
| VIZ-A-04 | `displayMode ≠ Fact ⇒ claimId` present | Adapter gate throws |
| VIZ-A-05 | `displayMode = Hypothesis ⇒ counterArgument` present | Adapter gate throws |
| VIZ-A-06 | `displayMode = Fog ⇒ fogReason` present | Adapter gate throws |
| VIZ-A-07 | `footer` is always present, even when all counts are zero | Schema test |
| VIZ-A-08 | `contentHash` covers every field except itself | Recomputation test |
| VIZ-A-09 | `layoutHint` is optional; absence means adapter chooses | Two renders, one with/without hint |
| VIZ-A-10 | `preferences` never changes semantic content | Hash equality across preference variants |

## 4. The adapter contract

### 4.1 Gate (runs before anything is drawn)

```typescript
export function gate(spec: ViewSpec): void {
  for (const el of spec.elements) {
    if (!el.evidence) throw new VizError('ELEMENT_WITHOUT_EVIDENCE', el.id);
    if (el.displayMode !== 'Fact' && !el.claimId)
      throw new VizError('NON_FACT_WITHOUT_CLAIM', el.id);
    if (el.displayMode === 'Hypothesis' && !el.counterArgument)
      throw new VizError('HYPOTHESIS_WITHOUT_COUNTER', el.id);
    if (el.displayMode === 'Fog' && !el.fogReason)
      throw new VizError('FOG_WITHOUT_REASON', el.id);
  }
  for (const e of spec.edges) {
    if (!e.evidence) throw new VizError('EDGE_WITHOUT_EVIDENCE', e.id);
  }
}
```

`gate()` is the **only** honesty enforcement point in the viz layer. Renderers do not re-check; they trust that `adapt()` was only reached after `gate()` passed.

### 4.2 Adapt (semantic → G6 data)

```typescript
export function adapt(spec: ViewSpec): GraphData {
  gate(spec);
  return {
    nodes: spec.elements.map(el => ({
      id: el.id,
      data: {
        elementKind:  el.elementKind,
        displayMode:  el.displayMode,
        label:        el.label,
        evidence:     el.evidence,
        claimId:      el.claimId,
        counterArgument: el.counterArgument,
        fogReason:    el.fogReason,
        salienceWeight: el.salience.weight,
        fields:       el.fields,
        parentId:     el.parentId,
      },
    })),
    edges: spec.edges.map(e => ({
      id: e.id,
      source: e.source,
      target: e.target,
      data: {
        edgeKind: e.edgeKind,
        displayMode: e.displayMode,
        evidence: e.evidence,
        counterArgument: e.counterArgument,
      },
    })),
    combos: (spec.groups ?? []).map(g => ({
      id: g.id, data: { label: g.label, kind: g.kind },
    })),
  };
}
```

G6's data model places business fields under `data` and visual fields under `style`. The adapter follows that split exactly: **semantics go to `data`, appearance is decided by `graphOptions`.**

### 4.3 Graph options (semantic → visual mapping)

```typescript
export function graphOptions(spec: ViewSpec): GraphOptions {
  return {
    data: adapt(spec),

    // ── Epistemic encoding: the visual law ──────────────────────────
    node: {
      type: (d) => NODE_TYPE[d.data.elementKind] ?? 'circle',
      style: {
        lineDash: (d) => DASH[d.data.displayMode],        // Fact none, Inference [6,4], Hypothesis [2,4], Fog [1,3]
        stroke:   (d) => STROKE[d.data.displayMode],
        lineWidth:(d) => d.data.displayMode === 'Fact' ? 2 : 1.5,
        size:     (d) => 20 + d.data.salienceWeight * 40,
        labelText:(d) => d.data.label,
        labelPlacement: 'bottom',
        badge:    (d) => d.data.displayMode === 'Fog'
                          ? [{ text: '?', placement: 'right-top' }] : [],
      },
    },
    edge: {
      style: {
        lineDash: (d) => EDGE_DASH[d.data.displayMode],
        endArrow: true,
        labelText: (d) => d.data.edgeKind,
      },
    },

    // ── Layout: pass-through to G6's layout registry ────────────────
    layout: spec.layoutHint
      ? { type: spec.layoutHint.strategy, ...spec.layoutHint.params }
      : autoLayout(spec),          // acyclic → dagre, dense → force, tree → compact-box

    // ── Plugins: fisheye is one entry ───────────────────────────────
    plugins: buildPlugins(spec.preferences),

    renderer: spec.preferences?.renderer ?? 'canvas',
  };
}

function buildPlugins(p: Preferences = {}): PluginOptions[] {
  const out: PluginOptions[] = [];
  if (p.fisheye) {
    out.push({
      type: 'fisheye',
      key: 'cie-fisheye',
      trigger: p.fisheye.trigger ?? 'pointermove',
      d: p.fisheye.d ?? 1.5,
      r: p.fisheye.r ?? 120,
      ...p.fisheye,
    });
  }
  if (p.minimap) out.push({ type: 'minimap', key: 'cie-minimap', size: [240, 160] });
  if (p.edgeBundling) out.push({ type: 'edge-bundling', key: 'cie-bundling' });
  if (p.history) out.push({ type: 'history', key: 'cie-history' });
  return out;
}
```

`buildPlugins` is deliberately small because **G6 owns the plugin implementations**. Fisheye is configured by its documented options — `trigger`, `d`, `r`, `maxR`, `minR`, `maxD`, `minD`, `scaleRBy`, `scaleDBy`, `showDPercent`, `style`, `nodeStyle`, `preventDefault`. There is no custom lens geometry, no coordinate transform, and no hit-testing in the adapter.

### 4.4 Adapter requirements

| ID | Requirement | Acceptance |
|---|---|---|
| VIZ-B-01 | `gate()` runs before `adapt()` on every render path | Unit test: unevidenced element throws, graph never constructed |
| VIZ-B-02 | `adapt()` is pure | Same spec twice → deep-equal `GraphData` |
| VIZ-B-03 | `graphOptions()` is pure | Same spec twice → deep-equal options |
| VIZ-B-04 | No `ViewKind` branching anywhere in the adapter | Static analysis: adapter has no chart-name string constants |
| VIZ-B-05 | Adding a new `ElementKind` requires only a new `NODE_TYPE` entry | New kind test: renders without touching adapter logic |
| VIZ-B-06 | Adding a new layout requires only a new `LayoutHint.strategy` string | Layout swap test |
| VIZ-B-07 | `preferences` never alters `GraphData` | Hash equality test |

## 5. Extension surface requirements

G6 registers extensions under ten categories, and the first registration for a given name wins. The platform treats every category as an open rendering surface:

| ID | Requirement | Notes |
|---|---|---|
| VIZ-C-01 | Every built-in G6 node type is usable without adapter change | `circle`, `diamond`, `donut`, `ellipse`, `hexagon`, `html`, `image`, `rect`, `star`, `triangle` |
| VIZ-C-02 | Custom node types are registered via `register(ExtensionCategory.NODE, name, impl)` | A new chart-specific shape is a registration, not a schema change |
| VIZ-C-03 | Custom edge types are registered via `register(ExtensionCategory.EDGE, …)` | Same |
| VIZ-C-04 | Custom combos are registered via `register(ExtensionCategory.COMBO, …)` | Used for swim lanes and owner columns |
| VIZ-C-05 | Custom layouts are registered via `register(ExtensionCategory.LAYOUT, …)` | Used for journey, terrain, matrix |
| VIZ-C-06 | Custom plugins are registered via `register(ExtensionCategory.PLUGIN, …)` | Used for gap overlay, footer overlay |
| VIZ-C-07 | Registration is idempotent and deterministic | First registration wins; duplicate name test |
| VIZ-C-08 | Unregistered name in `node.type` falls back to `circle`, never crashes | Fallback test |
| VIZ-C-09 | `getExtension`/`getExtensions` are used by tests to prove registration | Registry introspection test |

**VIZ-C-10 (the "not limited to 16" clause):** The number of renderable charts is bounded only by the number of registered extensions. There is no enumeration of charts in the adapter, the ViewSpec, or the CIE producer.

## 6. Layout requirements

G6 ships more than twenty layouts — `antv-dagre`, `circular`, `combo-combined`, `concentric`, `d3-force`, `d3-force-3d`, `dagre`, `fishbone`, `force`, `force-atlas2`, `fruchterman`, `grid`, `mds`, `radial`, `random`, `snake`, `compact-box`, `dendrogram`, `mindmap`, `indented`. The adapter must not reinvent any of them.

| ID | Requirement | Acceptance |
|---|---|---|
| VIZ-D-01 | `layoutHint.strategy` is passed verbatim to `layout.type` | Spy on `graphOptions` |
| VIZ-D-02 | `layoutHint.params` is spread into the layout config | Dagre test with `rankdir: 'LR'` |
| VIZ-D-03 | Absent hint → deterministic auto-selection from graph shape | Acyclic → `dagre`; tree → `compact-box`; dense → `force` |
| VIZ-D-04 | Layout swap never changes element ids or display modes | Dagre vs fruchterman hash test |
| VIZ-D-05 | Every layout in G6's registry is addressable by name | Parametrised test over the layout list |
| VIZ-D-06 | Custom layout registered by name is usable via `layoutHint.strategy` | Journey layout test |
| VIZ-D-07 | Layout computation runs under `enableWorker` where available | Config assertion |

**VIZ-D-08:** No layout algorithm is implemented in CIE or in the adapter. Geometry is G6's responsibility, always.

## 8. Epistemic encoding requirements

The visual law is fixed; the visual vocabulary is open.

| Display mode | Stroke | Glyph | Word |
|---|---|---|---|
| Fact | solid | ● | "Fact · statically proven" |
| Inference | dashed `[6,4]` | ◐ | "Inference · derived from cited evidence" |
| Hypothesis | dotted `[2,4]` | ○ | "Hypothesis · cannot be proven statically" |
| Fog | hatched `[1,3]` | ? | "Fog · not determinable from static analysis" |

| ID | Requirement |
|---|---|
| VIZ-F-01 | Encoding is redundant: stroke + glyph + word, never colour alone |
| VIZ-F-02 | `lineDash` is computed from `datum.data.displayMode`, not from node type |
| VIZ-F-03 | A custom node type must still honour `lineDash` and `stroke` |
| VIZ-F-04 | Hypothesis nodes render their `counterArgument` in the inspector, not on canvas |
| VIZ-F-05 | Fog nodes always carry a visible `fogReason` |
| VIZ-F-06 | The footer is rendered by a registered overlay plugin, outside the graph canvas |
| VIZ-F-07 | Contrast ≥ 4.5:1 for labels and ≥ 3:1 for display modes in light, dark, high-contrast |

### TC-03 — Custom node type, registered, used by `node.type` callback

**Engine surfaces:** `register(ExtensionCategory.NODE, name, impl)`; dynamic `node.type`

```ts
import { Graph, register, ExtensionCategory, Circle } from 'https://esm.sh/@antv/g6@5';

class ConceptNode extends Circle {
  render(attributes, container) {
    super.render(attributes, container);
    // draw a small "concept" badge; the epistemic stroke is untouched
    this.upsert('badge', 'text', {
      text: 'C', x: 0, y: -attributes.size / 2 - 8,
      fill: '#bc8cff', fontSize: 11, textAlign: 'center',
    }, container);
  }
}
register(ExtensionCategory.NODE, 'cie-concept-node', ConceptNode);

const graph = new Graph({
  container: 'c',
  data,
  node: {
    type: (d) => d.data.elementKind === 'concept' ? 'cie-concept-node' : 'rect',
    style: {
      lineDash: (d) => DASH[d.data.displayMode],
      stroke:   (d) => STROKE[d.data.displayMode],
      size: (d) => d.data.elementKind === 'concept' ? 44 : [160, 36],
      labelText: (d) => d.data.label,
    },
  },
  layout: { type: 'fruchterman', gravity: 10, speed: 5 },
});
await graph.render();
```

**Expected render:** the `Checkout` node is a circle with a `C` badge above it and the same solid green Fact stroke; every other node remains a rectangle with its dashed/dotted/hatched stroke; the layout is force-directed.

**Assertions:**

| # | Assertion | How |
|---|---|---|
| 1 | Extension is registered | `getExtension(ExtensionCategory.NODE, 'cie-concept-node')` is defined |
| 2 | Checkout uses the custom type | `graph.getElementRenderStyle('checkout').type` or inspect shape |
| 3 | Custom node still obeys epistemic encoding | `lineDash` equals `undefined` for Fact |
| 4 | Fruchterman layout produced non-grid coordinates | At least 3 distinct x and y values |

## 15. Non-goals

| Excluded | Reason |
|---|---|
| Reimplementing any G6 layout | G6 owns geometry; the adapter passes names and params |
| Reimplementing fisheye lens maths | G6's plugin owns the lens |
| A fixed enumeration of chart types in CIE | The registry is the enumeration |
| Chart-specific code in the ViewSpec producer | `ViewSpec` is a semantic graph, not a chart spec |
| A custom graph renderer | Canvas/SVG/WebGL are G6's renderers |
| Enforcing honesty inside each renderer | The adapter gate is the single enforcement point |
| Supporting a chart that G6 cannot be extended to draw | If G6 cannot draw it, the platform cannot promise it |

## 17. One-sentence summary

**CIE emits a semantic graph; the adapter enforces honesty once; G6 renders it with any registered node, edge, layout, or plugin — so fisheye is one configuration entry, new charts are registrations rather than schema changes, and the visual surface is bounded only by what G6 can be extended to draw.**
